# api-project

Тести Dojo Articles (`http://104.168.59.50`), у яких передумови готуються через API,
а в браузері лишається лише дія користувача.

## Запуск

```bash
npx playwright test tests/api-project/e2e/add-to-favourite.spec.ts --project=api-project-e2e
```

Ручна підготовка акаунта не потрібна: кожен запуск створює нового користувача через API
(`username` та `email` генерує `faker`), тож повторні запуски не конфліктують.

## Структура

| Що | Де |
|---|---|
| Тест зміни аватарки | `e2e/add-to-favourite.spec.ts` |
| API-операції (реєстрація, логін) | `controllers/UserController.ts` |
| Дії та перевірки на сторінці | `controllers/PageControllers.ts` |
| Фікстури `register`, `token`, `login`, `request` | `fixtures/base-fixture.ts` |
| Адреса середовища | `baseURL` проєкту `api-project-e2e` у `playwright.config.ts` |

**Ланцюжок фікстур (усі працюють з одним користувачем):**

1. `register` — створює користувача через `POST /api/users`, повертає надіслані дані
   і відповідь сервера.
2. `token` — бере `user.token` з відповіді реєстрації.
3. `login` — кладе цей токен у браузерний контекст через storage state.
4. `request` — API-контекст із заголовком `Authorization` цього ж користувача.

## Дослідження

### 1. Запити (DevTools → Network)

| Дія в UI | Метод і URL | Тіло запиту | Статус | Відповідь |
|---|---|---|---|---|
| Реєстрація | `POST /api/users` | `{ "user": { "username", "email", "password" } }` | 201 | `{ "user": { "email", "username", "bio", "image", "token" } }` |
| Вхід | `POST /api/users/login` | `{ "user": { "email", "password" } }` | 200 | така сама структура `user` |
| Збереження профілю | `PUT /api/user` | `{ "user": { "image": "<URL>" } }` (для аватарки достатньо поля `image`) | 200 | оновлений `user`, `image` дорівнює надісланому URL |

- Запит без заголовка `Authorization` до `GET /api/user` повертає `401`
  з повідомленням «Потрібна авторизація».
- Реєстрація та вхід не потребують авторизації. Збереження профілю потребує.
- Назви `GET /api/user` і `PUT /api/user` збігаються, тому в мережі їх відрізняє лише метод:
  в очікуванні відповіді слід вказувати `PUT`.

### 2. Де зберігається стан входу

- Токен лежить у **`localStorage`** під ключем **`qa-dojo.token`** (origin `http://104.168.59.50`).
  Cookies для входу не використовуються.
- Значення збігається з `user.token` у відповіді `POST /api/users` та `POST /api/users/login`
  (звірено в DevTools → Application → Local Storage).
- Як визначено: після входу через UI у Application → Local Storage з'являється ключ
  `qa-dojo.token`, а в Network усі наступні запити несуть заголовок з цим токеном.

### 3. Як токен передається в наступних запитах

Заголовок `Authorization: Token <токен>` (саме слово `Token` і пробіл перед значенням,
не `Bearer`). Без пробілу сервер відповідає `401`.

### 4. Передумови для UI-сценаріїв

| Сценарій | Що готуємо через API | API-операція | Що лишається в UI |
|---|---|---|---|
| Зміна аватарки (реалізовано) | Новий користувач і його токен у браузері | `POST /api/users` (токен із відповіді) + storage state у `localStorage` | Ввести URL у налаштуваннях, зберегти, перевірити зображення до і після перезавантаження |
| Додавання статті в обране | Користувач і стаття | `POST /api/articles` (відповідь `201`, у ній `slug`) | Відкрити сторінку статті, натиснути кнопку «обране», перевірити, що стаття є у вкладці Favorites профілю |
| Редагування статті | Користувач і стаття | `POST /api/articles` | Відкрити статтю, натиснути «Edit» (`edit-article-button`, веде на `/articles/editor/<slug>`), змінити заголовок, зберегти, перевірити новий заголовок на сторінці статті |

Для «обраного» перевірено, що `POST /api/articles/<slug>/favorite` доступний і
повертає `200`, тобто стан «у обраному» можна відтворювати й через API, коли потрібно
не перевіряти саму дію кнопки.

Для редагування перевірено, що `PUT /api/articles/<slug>` з тілом
`{ "article": { "title": ... } }` повертає `200`, а `slug` змінюється разом із заголовком
(новий `slug` дорівнює новому заголовку), тому після редагування сторінку статті треба
відкривати за новим `slug`. Сторінка статті має кнопки `edit-article-button` та
`delete-article-button`.

## Спостереження

### Галочка "I agree to the terms of use" працює лише в UI

- Форма реєстрації відправляє `POST /api/users` з тілом лише з трьох полів:
  `{ "user": { "username", "email", "password" } }`.
- Стан чекбокса в запит не потрапляє, тому перевірка відбувається тільки на клієнті:
  UI не дає натиснути кнопку без галочки.
- Сервер цю умову не вимагає: користувач, створений напряму через API без жодної згоди
  з умовами, реєструється успішно (так працює фікстура `register`).

**Наслідки:**

- Для підготовки даних через API це зручно: UI-перевірки обходити не потрібно.
- Сценарій «реєстрація неможлива без галочки» можна перевірити лише через UI.
- Різниця між валідацією в UI та на сервері — потенційне зауваження до продукту.

> Перевірено тільки те, що реєстрація проходить без цього поля.
> Інші серверні валідації (довжина пароля, формат email тощо) не досліджувались.

### Пряме відкриття закритих сторінок кидає на логін

`goto("/articles/settings")` (і `/articles/editor`) для залогіненого користувача
перенаправляє на `/articles/login`: застосунок перевіряє доступ раніше, ніж підтягує
користувача з токена. Тому в тестах налаштування відкриваються через інтерфейс
(`/articles` → `nav-profile` → «Edit profile»), а після `reload` цей шлях повторюється.
